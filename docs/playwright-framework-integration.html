How it works

Three steps. The agent handles the rest.

The full pipeline — recording to passing test — requires one action from the engineer.

Step 1 · Record
Capture the user flow in Jam

An engineer — or anyone on the team — records a user flow in Jam. The recording captures every click, keystroke, and page transition exactly as it happened.

→
Step 2 · Share
Give the agent the URL

Share the Jam recording URL with the AI agent. That is the only required input. No test specification. No selector hunting. No framework knowledge required.

→
Step 3 · Receive
A passing test is delivered

The agent reads the recording, generates or updates the test, runs it, heals failures, and hands back a framework-compliant, passing result. You review. Done.

Create or update — automatically decided — The agent checks whether a test already exists for the recorded flow. If one is found, it patches only what changed. If not, it generates all five layers from scratch. Existing passing tests are never touched unless their selectors are stale.

What makes it possible

Three sections working together

The pipeline is built on three independent components. Each answers a question the others can't. All three are active on every run.

Section A
Framework Skills

What the agent knows about your codebase conventions — the rules, patterns, and architecture it must follow when writing any test.

Section B
Jam Recording

What the test should cover — a structured summary of what the user did, which elements were touched, and what success looks like per step.

Section C
Playwright CLI

The verification layer — resolves ambiguous selectors against the live DOM, runs the spec, and heals failures before the result is delivered.

Section A
Framework Skills
Execution Rules

A structured set of Markdown files the agent reads before writing a single line. They encode every architectural decision the team has already made: how tests are layered across five files, which base classes to extend, which factory methods to call, how XPath locators must be structured, and which folder a given priority level belongs in.

The agent doesn't invent conventions — it reads them. These files are the definition of "correct" for this codebase. Any instruction-following model that receives them produces the same architecture — making the pipeline model-agnostic.

Files Loaded
  • SKILL.md — routing and entry point
  • core-framework.md — architecture rules
  • templates.md — five-layer templates
  • validation-checklist.md — acceptance criteria
  • locator-rules.md (when needed)

Section B
Jam Recording
Flow Capture

A structured JSON summary of what a real user did in the browser, produced by the Jam CLI from a video recording. The agent calls jam get intents <id> — not the raw event stream — and receives organized intent data: the user's goal, each key action with its CSS selector and entered value, the expected visual outcome per step, and per-phase success and failure criteria.

The engineer doesn't write a test specification. The recording is the specification. A 34-second login flow with 4 phases produces 7,293 bytes (~1,823 tokens) of structured intent data — selectors and assertions included, ready to translate.

Primary Command
jam get intents <recording-id>
Fallback: jam get events --limit 50
filtered + condensed if intents not ready

~456 tok / phase

Duration does not affect cost
Without this:The agent explores the live app blind — 3–5 full DOM snapshots (~4,000–8,000 tok each) — to reconstruct what the user did, then guesses at assertions. Token cost rises from ~1,823 to ~18,307 for the same flow. Accuracy is lower.
Section C
Playwright CLI
DOM Resolution & Execution

The Playwright test runner, augmented with a session-based debug CLI, serves two roles. First: resolving ambiguous selectors. Jam gives CSS; the framework needs XPath. Most translate deterministically — an id attribute, a stable text match. When translation is uncertain, the agent emits SELECTOR_NEEDED and runs a targeted playwright-cli eval to resolve it precisely rather than guessing.

Second: execution and healing. After generation, the agent runs the spec. On failure it attaches via --debug=cli, inspects the DOM at the failure point, patches only the Page Object, and re-runs — all within the same pipeline that generated the test.

Key Commands
  • playwright-cli snapshot — full DOM
  • playwright-cli eval — targeted query
  • npx playwright test <spec>
  • --debug=cli — attach on failure
Token Cost
~0 base cost
Only invoked on SELECTOR_NEEDED
or test failure (~25% of tests)
Expected value: ~1,750 tok/test
Without this:CSS-to-XPath translation is unverified — the agent guesses, producing brittle locators. Tests are never executed in the same run, so failures surface in CI rather than being caught and healed before delivery. Engineers debug each failure manually.
